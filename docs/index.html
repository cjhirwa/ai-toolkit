Overview—Most LLM tooling is written for the happy path, yet production systems meet rate limits, provider outages, scanned documents, interrupted jobs, confidential data and unbounded bills. This toolkit covers document ingestion, retrieval, evaluation, query routing and agents, and routes every model call through one gateway that owns failures, cost, privacy and tracing. Failures are explicit rather than silently absorbed, spending is bounded, logs are private by default, and evaluation results come with confidence intervals and survive crashes.

IIntroduction

An LLM application is a distributed system built around an unreliable, metered and non-deterministic dependency. Common defaults treat that dependency as an ordinary function call: retry anything, switch models when one fails, average whatever scores come back. Each default is reasonable on its own. Together they produce systems that look healthy while answering from the wrong model, losing data and overstating improvements.

This project takes the opposite position: a failure should be visible, bounded and attributable. Rather than a framework, it is a set of small packages with explicit contracts that share one gateway, so the rules for failure, cost and privacy are written once and apply everywhere.

IIArchitecture

The packages form three stages (Fig. 1). Build turns documents into a searchable index, Serve routes and answers user queries, and Measure generates test questions, benchmarks retrieval and scores answers. No component calls a model provider directly; every call goes through the gateway.

IIIFailure Semantics

The gateway decides what happens when a call fails, once and the same way for every package (Fig. 2). Only transient failures (throttling, server errors, timeouts, dropped connections) are retried or passed to a fallback model; a bad request or an authentication error surfaces immediately, because answering from another model would hide it. A reply cut off at the token limit is reported as truncated rather than treated as an answer. In ingestion, a page that cannot be read is skipped on its own instead of taking its document with it. The query router sends a query it cannot classify to a cautious route, such as asking for clarification, never to the normal answer path.

IVCost and Concurrency

Every concurrent job in a process (evaluation, OCR, batch generation) draws from one shared rate and concurrency budget per provider, instead of each backing off on its own after being throttled. Spending can be capped per client and per day, and the daily cap holds across separate processes because it is computed from the shared call log. Work that has been paid for once is not paid for again: embeddings and OCR results are cached by content, so rebuilding an index or re-ingesting a document reuses earlier results (Table II).

VMeasurement

An evaluation tool that misleads is worse than none, so each run is built to be reproducible and comparable. Examples are identified by their content rather than their position, so editing a dataset never mismatches results. Two runs are compared with paired bootstrap confidence intervals [3], and a change is reported as significant only when its interval excludes zero. Results are saved as they are produced, so an interrupted run resumes where it stopped, and every run records the models, data and code version that produced it. Retrieval labels are stored as positions in the source document rather than chunk identifiers, so different chunking strategies can be compared against the same labels.

VIModel Independence

Behaviour should not change silently when a different model is configured. Similarity scores differ between embedding models, so a fixed routing threshold would route the same query differently under each one; the router therefore calibrates its threshold from its own examples. PDFs carry no section markup, so the ingester recovers section headings from typography (font size and weight), giving chunks from PDFs the same section context as those from DOCX or HTML.

VIIPrivacy and Security

Private by default

Logs record metadata such as model, tokens, cost and latency. Prompts and replies are kept only when explicitly enabled, and caches store no document text.

Untrusted documents

Retrieved passages are fenced off in prompts and marked as reference material, limiting indirect prompt injection [4].

Authenticated services

Network-facing MCP servers [6] require a token and refuse to serve beyond the local machine without one.

Contained configuration

Settings are read only from within the project, and ingestion limits file sizes and page counts.

VIIIEngineering Practice

The test suite runs offline against a simulated provider, and contract tests check each provider adapter against the SDK's own response types. Continuous integration runs the tests on Linux and Windows together with linting, type checking and a dependency vulnerability audit, and a daily job makes real provider calls. Every model call emits an OpenTelemetry span [5] with its tokens, cost, retries and errors. Releases follow semantic versioning.

IXLimitations

  • Answer quality has not yet been measured on a human-reviewed test set; the results above concern engineering behaviour.
  • Section-heading recovery is heuristic and may need tuning for unusual PDF layouts.
  • Dense retrieval runs in memory, which suits corpora up to a few hundred thousand chunks.
